## 监控服务
监控服务对支付申请单各生命周期进行监控，并且通过控制台可以直观看到支付申请单各项监控指标。

监控指标触发告警规则时，可以进行制定告警策略进行告警。

评价一个监控系统的好坏最重要三要素是：监控粒度、监控指标完整性、监控实时性。
从系统分层体系可以把监控系统分为三个层次：

+ 业务层： 业务系统本质目的是为了达成业务目标，因此监控业务系统是否正常最有效的方式是从数据上监控业务目标是否达成。
  - 对业务运营数据进行监控，可及时发现程序 bug 或业务逻辑设计缺陷，比如数据趋势、流量大小等。
  - 业务系统的多样性决定了应由各个业务系统实现监控指标开发。

+ 平台层： 对应用的整体运行状况进行了解、把控，如果将应用当成黑盒子，开发和运维就无从知晓应用当前状态，不能及时发现潜在故障。 
  - 应用监控不应局限于业务系统，还包括各种中间件和计算引擎，如 ClickHouse、ElasticSearch、redis、zookeeper、kafka 等。
  - 常用监控数据：JVM 堆内存、GC、CPU 使用率、线程数、TPS、吞吐量等，一般通过抽象出的统一指标收集组件，收集应用级指标。

+ 系统层： 实时掌握服务器工作状态，留意性能、内存消耗、容量和整体系统健康状态，保证服务器稳定运行。 
  - 监控指标：内存、磁盘、CPU、网络流量、系统进程等系统级性能指标。

平台层、系统层可有kubernetes容器层面处理，本次考虑从业务层进行监控告警处理。



## 监控系统设计
对监控的全流程分析，可发现监控服务全流程架构分为：采集、存储、分析、展示、告警等。

+ **数据采集**： 通过配置数据源查询目标数据库、通过Agent方式及时上报监控数据等。

+ **数据存储**：主要存储在MySQL上，考虑存储最大周期。

+ **数据分析**：监控服务提供图形化、时间轴等相关监控信息，方便分析系统目前运行情况。

+ **数据展示**：Web页面多维度展示。

+ **监控告警**：IM报警、邮件、短信等多维度多方式。

+ **告警处理**： 接收到告警后进行快速处理，根据告警级别不同，制定不同处理预案指引；重要、重要不紧急等。



在重要监控指标项章节，我们将详细介绍每一层级组件的监控指标含义和阈值等。

### 名词解释

**监控事件主体** : 支付申请单

**生命周期节点**: 支付申请单触发监控的埋点时机。

**事件元数据**: 监控事件主体，到达某生命周期节点时所产生的元数据，该数据所谓事件主体的基本监控单元，上送监控服务。

**监控指标**: 对监控事件元数据，按照某些维度进行统计、汇总；触发监控规则时可进行告警处理，未触发监控规则时可进行各维度统计展示。

**告警规则**: 设置既定规则维度、定时扫描监控指标数据，触发规则时进行产生告警事件。
 + 周期：原始值、最大值、最小值、求和等
 + 次数：连续1次、连续2次、连续N次
 + 对比逻辑：大于等于>= 、小于等于<=、大于> 、小于< 、等于=
 + 触发值：数字、字符串
 + 告警频次：每N单位触发1次，单位：分钟、小时
 + 告警级别：紧急、重要、提示；根据配置租户级别、要客列表设置不同告警级别。



**告警事件**: 触发告警规则所产生的告警事件；事件可通过通知规则进行设定组别通知。

**通知规则**: 设置告警事件通知规则，按照组别、重要程度、等级进行通知。
 + 统计类规则：按周、按月发送监控指标周报、月报。
 + 监控类规则：按照通知规则进行周期性通知，IM通知、短信通知等。
